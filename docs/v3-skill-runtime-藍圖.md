# Indify v3 — Skill Runtime 落地藍圖

> **提案 · 未定稿 · 待用戶拍板**

## 0. 結論先行

把 Dify 的 workflow 從「要操作的面板」重新定位成「你擁有的 skill」。Dify 退到幕後當技能工廠 + 運行時。你只管說一句話,剩下由 Agent 選 skill、填參、跑、驗、報;不滿意就繼續聊,就地改。

tool 那半已商品化(Dify 原生雙向 MCP、Service API、LangGraph subgraph-as-tool);**skill 那半是真空**——自描述、漸進式披露、副作用分級、可改進閉環,幾乎沒人做。這就是 v3 要佔的位。

## 1. 背景與定位

工作區 Indify 已完成:M0–M4 基線 + v2 三特性(F2 兩段式計劃 / F3 實時流 / F1 附件+OCR),用自然語言生成/修改 Dify 1.16.1 工作流,就地寫回原生畫布。設計見 DESIGN.md(狀態「已實現」),IR 契約在 §6,DSL 適配層在 §5.4。

現在把目標再抬一層:工作流不再是畫布,而是可調用、可自述、可改進的能力。

## 2. 三層架構(已定調)

| 層 | 內容 | 狀態 |
|---|---|---|
| L0 | Dify workflow → MCP tool / Service API | 免費已存在,不開發 |
| L1 | 技能卡 manifest(SKILL.md 式) | 全新 |
| L2 | Agent 技能註冊中心 + 調用循環 + 改進循環 | 全新;改進循環複用 U2/U3 |

## 3. 問題一:做完得到什麼

五件可交付物,逐條寫清:

1. **技能卡 manifest 標準**。每個 workflow 一張,字段:`name` / `description` / `when-to-use` / `input schema` / `output schema` / `side-effects` 分級 / `cost` / `how-to-verify`。
2. **技能註冊中心**。自動掃描 Dify 應用,生成並維護技能卡。入出參 schema **直接從 workflow 的 start/end 節點變量反推,不用手寫**。
3. **執行適配器**。DSL 適配層的兄弟組件,用 Service API(或 MCP)跑 workflow、抓結果、做成功判定。
4. **調用循環**。住在 Agent 裡:選 skill → 填參 → 跑 → 驗 → 報。
5. **改進閉環**。直接複用 Indify 的 U2/U3 就地改,不新造。

## 4. 問題二:用戶怎麼用

**Before(現狀)**:打開 Dify → 進應用 → Run 頁 → 手填變量 → 跑 → 看結果。

**After(做完)**:任意聊天框一句話 → Agent 選 skill → 缺參就反問 → 觸發副作用動作停下要確認 → 跑完用自然語言回報 → 不滿意繼續聊著改。

核心轉變一句話:**工作流從「要操作的面板」變成「你擁有的技能」,Dify 退到幕後當技能工廠 + 運行時。**

## 5. 貫穿例子:發票報銷審批

Workflow:OCR → 校驗 → 分類 → 發郵件通知財務。

1. 用戶:「把這張發票走報銷審批」。
2. Agent 讀技能卡,發現缺「部門」參數,反問:「這筆報銷掛哪個部門?」
3. 用戶補「市場部」。Agent 填好參數,一路跑到「發郵件給財務」——這是副作用動作,**停下要確認**。
4. 用戶確認。跑完,Agent 回報:「審批通過,郵件已發,回執號 XXXX」。
5. 用戶不滿意:「加一個金額 > 5000 需總監加簽的節點」。
6. 複用 Indify 就地改 → 再跑。

## 6. 推薦默認(待拍板)

- 執行側先上 **manifest + Service API 跑通最小閉環**;MCP 出口預留在同一真相源,不阻塞。
- 粒度 **一個 workflow = 一個 skill(1:1)** 起步,先跑順再談組合。
- 入出參 schema 一律反推,不引入手寫模板。

## 7. 非目標(明確不做)

- 不做多用戶 / SaaS。
- 不做技能市場。
- 改結構仍是「半自動 + 人審」,對齊既有紅線:不 fork Dify、不改源碼、渲染交給原生 Dify。
